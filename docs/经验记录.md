# 经验记录

## 2026-09-23 — AccessEvent 三原语落地后 Soft=0 TPS 仍低于 1.5

**问题：** 统一访问学习 v1 + v1.1 落地后，焦点块 SpecFence 相对 OCC 的 TPS 比没有到 1.5。

**表现：** release、LTO off、N=5、请求 8 核（宿主 4 核）、Soft=0 Instant-off、reuse median。`estimate_block_sf=0`，`soft_wait_arms=0`，SpecFence `occ_picks=0`，`seq≡par`。3356896 ratio **0.671**（SF 116903.6 / OCC 174278.6，墙时 1.506 / 1.010 ms）。15274915 ratio **0.719**（SF 151063.5 / OCC 210072.6，墙时 8.116 / 5.836 ms）。薄块 reuse 的 `yield_ok` 是 0–1，`raw` 是 0–1，FullReplay 0–2。大块 reuse 的 `yield_ok` 约 7，`raw` 7–33，FullReplay 2–6，`yield_deadlock` 曾到 24。WAW/WAR 计数很高（大块 waw≈139，war≈2850），链长仍是 17 与 77，起点到终点占掉 SF 墙时的大部分。

**逻辑盲点：** 把 RAW/WAW/WAR 分类记进 IntraRecord，并在宿主读里对“已经能看见的未发布写者”自旋，并不等于关键链变短或反链填满核。第一波没有写集时读者看不到 Estimate，WaitTrueVersion 大多不触发；写者链仍按序占满 makespan。RetainHistory 的 pin 没有接到多版本丢历史的路径。现有 SF 调度税加在反链上，OCC 即使 abort 更多（薄块约 14，大块约 70–120）仍然更快。

**解决方案：** 保持 AccessEvent 三原语脊。下一刀砍长链：武装 ℓ 的剩余触及者在帧内等真 publish（目标是 reuse 的 `full_from_0` 归零），非触及者不要付 SF 调度税，用反链填核。不要加第四原语，不要用 Estimate 或 `next_task*` 门控 Avoid，不要把 Cross Prior 做成硬 Fence。本次数字来自 `specfence_3356896_compare` 的 `TPS_SUMMARY`，不是外推。

### 2026-09-23 续 — 强迫触及者等待，以及跳过 Estimate

**问题：** 上一刀的复测仍低于 1.5，并且有一次把 `seq≡par` 做坏了。

**表现：**

- 前驱一开工就 handoff 整条链（`37bd070`）：3356896 ratio **0.155**，15274915 ratio **0.127**。大块 `yield_deadlock=132`。协议仍在，但比基线更差。
- 只在发布时 handoff，并把 WAR pin 做成「不要把 Data 换成 Estimate」（`f285e7b`）：3356896 ratio **0.825**（seq≡par），15274915 ratio **0.798**（**seq≠par**）。`handoff` 16 / 76，`defer≈0`，`yield_ok` 仍接近 0。
- 把链上读者整表 park、写者开工再唤醒（`5e75350`）：seq≡par 恢复，`yield_ok` 仍是 0。3356896 ratio **0.574**，15274915 ratio **0.723**。
- 撤回停车、保留「先快照再 Estimate」（`663211d`）：3356896 ratio **0.690**（SF 120665.0 / OCC 174863.9，墙时 1.459 / 1.006 ms），15274915 ratio **0.707**（SF 162557.1 / OCC 229915.2，墙时 7.542 / 5.332 ms）。两边 `seq≡par`。末轮 `yield_ok` 0 / 4，`handoff` 16 / 76，`retain` 0 / 2，`defer` 0 / 0，`chain` 17 / 77。`est_block=0`，`soft=0`，`occ_picks=0`。

**逻辑盲点：**

- 跳过 Estimate 会让已经验证过的更高交易继续相信被中止的 incarnation。`finish_execution` 只在 `WroteNewLocation` 时才把 `validation_idx` 拉回来，同位置重写不会自动重验。
- 一个链写者大约几十微秒。把读者先 park、等写者进解释器再 `wake_idle`，读者到达宿主读时 tip 已经发布，`yield_ok` 不会涨，停车本身把链头到链尾拉开（薄块曾到 head 0.25 ms / tail 1.23 ms）。
- `handoff=链长-1` 只说明后继被排到队头，不说明墙时低于 OCC。薄块末轮链跨度约 0.42 ms（head 0.219 → tail 0.639），OCC 墙时 1.006 ms；SF 墙时 1.459 ms，多出来的是反链上的调度税，不是没覆盖的第四类冲突。

**解决方案：** 活条目在 abort 时仍然换成 Estimate；WAR 读者绑定过的原点先拷进 `retained_history`，只供该读者在 Estimate 窗口重读，验证仍因 Estimate 失败关闭。不把整表读者 park 进帧内等。下一刀应砍反链的 SF pick/validate 税，而不是再加 wait。数字来自同一次 `TPS_SUMMARY`。

## 2026-09-24 — AdmitShard：分核 Chase-Lev，税还在

**问题：** IdleStealWake 把全部 AdmitIndep 种进 worker 0 的一把 `Mutex<VecDeque>`。steal 接近 Ideal pure_indep（引用 147 / 1081），SF 墙不降。朴素 `tx % C` 又让每个核都从低索引开工，2 核上 15274915 `seq≠par`。

**表现：** `1fa3308`，Soft=0 Instant-off、release、LTO off、N=5、请求 8 核。同宿主把 `ac9e82d` 重跑作对照。AdmitShard 薄块 ratio **0.701**（SF 1.343 / OCC 0.942，span 0.299，tax 1.044，steal 61，local_pops 98）；大块 **0.737**（7.359 / 5.420，span 1.497，tax 5.862，steal 296，local_pops 877）。同宿主 IdleStealWake 是 0.621（1.562 / 0.969，steal 122）和 0.648（8.330 / 5.397，steal 1078）。两边 `seq≡par`，`spine_cores_max=1`，`est=0`，`soft=0`，`occ_picks=0`。2 核冷检两块各 4/4 `seq=par`。`steal_top_ns` 中位轮 12464 / 49620 ns，`end_block_ns` 96169 / 79889 ns。愿望线 1.5 未到。

**逻辑盲点：** 把「steal 次数高」当成反链没被吃；真正贵的是单所有者 Mutex。轮转播种看起来均衡，却让每个核的 LIFO 都碰到前缀，读集洞会打成必现错收据。分片之后 `pop_top` 的时间和 `end_block` 都远小于 tax，剩下的税不在这把锁上。第一次复用仍可能 defer 到几百或几千，中位墙不一定落在那一轮。

**解决方案：** 只把真 AdmitIndep 按索引切成连续等分。worker 0 的低段高索引先入，LIFO 先吃低前缀；其余段低索引先入，LIFO 先吃本段高端。所有者 `pop_bottom`，本地空了才 Chase-Lev `pop_top`。脊跳继续 `mark_wait`，不进可偷 deque。数字来自 `specfence_3356896_compare` 的 `TPS_SUMMARY`、同日志 focus span，以及同宿主 `ac9e82d` 重跑。

## 2026-09-24 — IdleStealWake 的 handoff 空转和轮转播种

**问题：** 在 `5af6822` 上加 IdleStealWake（本地 LIFO、跨核 FIFO steal、单槽 spine、精确唤醒）后，15274915 的并行收据和顺序执行不一致，并且有的 reuse 轮 `ordered_defer` 到上千。

**表现：** 槽被占用仍 `continue` 的那一版（`c272ea5`）：大块 ratio 0.567，SF 墙 8.991 ms，`seq≠par`，末轮 defer=1658。把 AdmitIndep 按核轮转播种后，2 核冷检 4/4 失败，第一笔分叉在 tx 92–102（Uniswap），并行把 gas 打满到 gas limit，顺序路径提前 revert。改成整块种在 worker 0 之后，2 核 8/8 `seq≡par`。8 核冷检本尖 6/8、基线 `5af6822` 同宿主 4/6，两边都不是 8 核必过。正式 N=5（tip `21802b1`）两边 `seq≡par`：3356896 ratio 0.673（墙 1.538/1.036），15274915 ratio 0.740（墙 7.776/5.756）。`spine_cores_max=1`。愿望线 1.5 未到。

**逻辑盲点：**

- pick 循环里把刚取到的 handoff 放回槽再 `continue`，同一等待 hop 会被连续认领，`defer` 涨、span 被拉长。没拿到槽的链成员不应写进槽。
- 每个 worker 的 deque 如果在播种时按核轮转，所有者 LIFO 都从低索引开工，前缀上的依赖交易叠在一起。基线的全局 deque 是一个核吃低端、其余核从高端 FIFO 偷。轮转破坏了这个顺序，潜在的读集洞会被打成必现错收据。
- 空闲时用 250µs `park_timeout` 且只要有人在跑就睡，会把空核一起唤醒，和 `force_idle_recover` 抢。只在确有 live producer 时 park。

**解决方案：** 槽被挡或 `try_acquire` 失败时归还槽并离开本次 pick。AdmitIndep 初始只进 worker 0 的 deque（高端先入，链头最后）。park 只在 `waiting_on_live_producer` 时发生，超时 20ms 只作漏唤醒的安全网。数字来自 `specfence_3356896_compare` 的 `TPS_SUMMARY` 和同日志的 focus span。

## 2026-09-24 — OCC 更快，是因为同一次 `run_pevm_tx` 更短

**问题：** Soft=0 大块 SF 约 7.0–7.2 ms、OCC 约 5.3–5.9 ms。首次 Opt 里约 90% 被记成两边都要付的解释器加写提交。要分清 OCC 是少做了执行，还是同一次调用更便宜。

**表现：** `59f98c9`，同一二进制，release、LTO off、N=5、请求 8 核、宿主 4 核、`taskset -c 0-3`。15274915 复用中位 SF **8.020** / OCC **5.823** / ratio **0.726**，`est=0`，`soft=0`，`occ_picks=0`，`spine_cores_max=1`，链端 116/1219。这轮绝对墙不替换锁定带 7.0–7.2 / 5.3–5.9。四次复用里 SF 成功执行 1236–1239 次，OCC 1304–1355 次；OCC abort 78–129，SF 9–12。`run_pevm_tx` 线程时间 SF 比 OCC 多 **2.85–4.90 ms**（约 4 µs/次）。`finish_execution` 多 **0.75–0.84 ms** 线程。OCC 的 pick 循环更长。2 核冷检两块 `seq=par ok`。`ge_1_5=false`。

**逻辑盲点：** 把「90% 在解释器里」读成「两边的解释器一样贵」。那 90% 是 SF 自己内部的桶，写提交和 `run_pevm_tx` 混在一起，也没有和 OCC 的同一次调用比。OCC abort 更多，仍然更早结束，所以差不在重复功。`finish_execution` 的差摊到 4 核大约 0.2 ms，对不上 1.3–1.9 ms。

**解决方案：** 停掉 Soft=0 读元数据跳过和 `finish_execution` 微刀。下一问只设计：把 `run_pevm_tx` 再拆成操作码和 VmDb，看多出来的约 4 µs 是不是 SF 读钩子。就算整段解释器差都去掉，墙也只靠近 OCC，ratio 到不了 1.5。详见 `docs/specfence-soft0-occ-faster-same-evm-dig.md`。

### 2026-09-24 续 — 拆开之后差在 Detect，不在操作码

**问题：** 同一次 `run_pevm_tx` 更贵。要分清多出来的时间是两边都付的 opcode，还是 SpecFence 的 VmDb / Detect。

**表现：** `3421771`，只加时钟，release、LTO off、N=5、请求 8 核、宿主 4 核、`taskset -c 0-3`。15274915 复用中位 SF **7.687** / OCC **5.795** / ratio **0.754**，`ge_1_5=false`。不替换锁定带。四次复用 opcode 线程差 −0.83 到 +0.35 ms；Detect 每次都为正，+1.18 到 +4.18 ms 线程。中位墙那一轮单次差是 opcode −0.23 µs、VmDb +0.61 µs、Detect +1.41 µs。OCC 的 Detect 为 0。两块 `seq=par ok`，`occ_picks=0`，`spine_cores_max=1`，`est=0`，`soft=0`。

**逻辑盲点：** 把「解释器更贵」读成「opcode 核更贵」。`run_pevm_tx` 里面 opcode 单次可以和 OCC 打平甚至更短；正差是 kept 的 spine peek 和 WaitOnce consult。首次 Opt 旧探针只看到几十次保留 Detect，是因为它没把链上和后续 incarnation 的全 Detect 算进去。

**解决方案：** 不改 Detect 或 VmDb 的控制流。产品切仍 CONDITIONAL，本轮不落地。opcode 主导才会停 Soft=0 元数据刀，这次不是。即使扣掉中位轮 Detect 的墙上界（约 0.44 ms），ratio 仍约 0.80，到不了 1.5。详见 `docs/specfence-soft0-interp-delta-split-probe.md`。

## 2026-09-24 — 自由核按气费换段会抬墙，段内 Ideal-ready 也不收 SF−Ideal

**问题：** 让 Ideal-ready 的 AdmitIndep 先上自由核，想把首次 `execute` 拉向 Ideal 反链时钟（`L_crit` 1.19 ms），从而降低 Soft=0 墙或缩小 SF−Ideal。

**表现：** `6516f6d`，release、LTO off、请求 8 核、宿主 4 核、`taskset -c 0-3`。换核 LPT 的薄块复用中位 SF **2.442** / OCC **1.120**，同机关刀是 **1.421** / **1.085**。拿掉换核、只在原段内重的先弹之后，大块两轮无探针复用中位 SF **8.268** 和 **7.627**，同机关刀 **7.399**。SF−Ideal **7.078** 和 **6.437**，锚 **5.875**。探针轮（不入锁定）1149 笔干净 Indep 到 1.19 ms 只填了 8.6%，中位进入 2.73 ms，主 blocker 全是 Admit。`ge_1_5=false`。报告里的进程 `seq=par ok`；同机关刀另有 8 次里 1 次 `seq!=par`，单次绿色不能当成新的确定性证明。

**逻辑盲点：** 把「按气费平衡到空核」当成填 Ideal 反链。换核破坏的是已经为了前缀收据稳住的下标段，薄块上多出来的是 defer 和 idle，不是更早的反链。段内重排也不把进入时刻从约 2.7 ms 拉回 0。span 有一轮变短（1.485）同时墙更长（8.268），短 span 不是墙降。

**解决方案：** 产品留下段内 Ideal-ready 优先和段内重者先弹，默认开，可用 `SPECFENCE_IDEAL_TIMED_ADMIT=0` 关掉。换核 LPT 不留。墙门 FAIL，不把这刀写成 SF−Ideal 已经缩小。详见 `docs/specfence-soft0-ideal-timed-admitindep-true-makespan.md`。

## 2026-09-24 — 单池和「远程 Ideal-ready 先于晚波」都没有收墙

**问题：** #56 的段内 Ideal-ready 重排没有缩小 SF−Ideal。挖到的根因是连续下标段把 Ideal-ready 锁在原核上：本段空了，别的段里还有。要改的是这份库存的可见性。

**表现：** 二进制 `f2e3344`，Soft=0 Instant-off、release、LTO off、请求 8 核、宿主 4 核、`taskset -c 0-3`。大块两轮刀开复用中位 SF **7.760** 和 **7.914**。同机 `SPECFENCE_GLOBAL_IDEAL_READY_POOL=0`（回到 #56 段内 Ideal-timed）是 **7.147** 和 **7.730**。同机再关 `SPECFENCE_IDEAL_TIMED_ADMIT`（下标段）是 **7.412**。SF−Ideal 刀开 **6.570 / 6.724**，同机关刀 **5.957 / 6.540**，下标段 **6.222**，锚 **5.875**。探针轮 fill@1.19 **9.9%**，中位进入 **2.976 ms**，1149 笔主 blocker 仍是 Admit。`ge_1_5=false`。薄块刀开两轮 **2.893** 和 **1.856**；同机下标段 **1.567**。报告里的 8 核进程和 2 核冷检都是 `seq=par ok`。更早的单池（`eeb3e37`，不是这只二进制）大块 **8.104**，对比当时刀关 **7.901**，并且 `seq≡par` 会抖；只让 worker 0 弹低前缀会挂。

**逻辑盲点：** 把「本段 Ideal-ready 空、远程还有」当成墙的主因，于是认为谁都能看见这份库存就会提前开工。单池把低前缀交给所有核，读集洞回到 `seq≠par`；把低前缀只留给 worker 0，链头又先被它拿走，低前缀没人弹，进程挂住。改成偷远程 Ideal-ready 再弹本核晚波之后，steal 确实发生了，fill 只从 8.6% 到 9.9%，进入时刻没有提前。同机 #56 形态的薄块复用中位两次都在 **16 ms** 一带（defer 数千），那是重者先弹加热之后的路径，不是这刀的墙。

**解决方案：** 不留单池，不留 worker-0 独占前缀，不留跨核 gas LPT。留下的是下标段加上「本段 Ideal-ready → 偷远程 Ideal-ready → 本段晚波」。默认开，`SPECFENCE_GLOBAL_IDEAL_READY_POOL=0` 回到 #56。墙门 FAIL-A，薄块第一轮另外落到 FAIL-B 那一档。不写成 SF−Ideal 已缩小，不宣称 ≥1.5。详见 `docs/specfence-soft0-global-ideal-ready-admit-pool.md`。
